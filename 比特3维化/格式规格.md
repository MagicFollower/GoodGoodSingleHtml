## 1. 设计目的与范围

### 1.1 要解决的问题

把任意文件重编码为一个自定义容器 `.bt3d`，使得：

1. **不可直接识别** —— `file` 之类的魔数嗅探器、hex 编辑器肉眼、自动分类索引器都无法判定原文件类型；
2. **可完整恢复** —— 无需任何外部信息（口令、密钥文件），仅凭容器自身即可逐字节还原原文件；
3. **具备三维解释** —— 容器内的每个比特都对应一个确定的体素坐标 `(x, y, z)`，可导出为 1024×1024 的层叠位图用于可视化；
4. **体积不膨胀** —— 总大小 = 原文件大小 + 128 字节，与文件大小无关，无向上取整。

### 1.2 明确不在范围内

| 不提供 | 理由 |
| --- | --- |
| 机密性 | 数据密钥明文存于头部（见 §12）。任何持有容器的人都能还原。 |
| 抗篡改认证 | `payload_tag` 的密钥就在头部，攻击者可重算。它只能检测**意外损坏**，不能检测**蓄意伪造**。 |
| 压缩 | v1 不含压缩挡位，`flags` bit5 保留给 v2。 |
| 流式/管道解码 | 秩压缩需要先扫一遍层内几何才能定位（见 §7），因此按层随机访问可行，按比特流式解码不可行。 |

### 1.3 一句话概括工作原理

> 原文件被切成 128 KiB 的层；每层的比特按**逆时针螺旋**填进 1024×1024 的平面格子；格子的光栅序号再经**密钥相关的仿射变换**打散；打散后的位置经**秩压缩**紧凑化以适配不满的末层；最后整层与 **ChaCha20 密钥流**异或后写入容器。

## 2. 术语与全局约定

### 2.1 术语

| 术语 | 定义 |
| --- | --- |
| 比特序号 `i` | 原文件展开成比特流后的全局下标，从 0 起，MSB-first（见 §2.2） |
| 层 `layer` | 1024×1024 = 1,048,576 个格子的平面，容纳 128 KiB |
| 层内序号 `s` | 比特在某层内的**填充顺序**下标，`s ∈ [0, 1048576)` |
| 格子 / 体素 | 层内的一个位置，坐标 `(x, y)`，`x, y ∈ [0, 1024)` |
| 光栅序号 `q` | 格子的行优先序号，`q = y · 1024 + x` |
| 散射序号 `r` | `q` 经仿射变换后的序号，`r ∈ [0, 1048576)` |
| 存储序号 `r'` | `r` 经秩压缩后真正落盘的序号 |
| 圈 `k` | 螺旋的第 k 圈，`k = 0` 是最外圈，`k = 511` 是最内圈 |
| 边长 `m` | 第 k 圈的边长，`m = 1024 − 2k` |
| DEK | data encryption key，32 字节，每文件随机生成，**明文**存于头部 |

### 2.2 五条硬性约定

这五条是跨实现互通的全部前提。任何一条不一致，两个实现都会「各自能还原、互相不能」。

| # | 约定 | 规范值 | 不一致的后果 |
| --- | --- | --- | --- |
| C1 | **字节序** | 头部所有多字节整数一律 **小端（LE）** | 头部字段全部读错 |
| C2 | **位序** | **MSB-first**：字节 `B` 的第 `j` 个比特（`j = 0..7`）是 `(B >> (7 − j)) & 1` | 每字节内 8 比特倒序；PNG 用 MSB-first，多数 CPU 位技巧默认 LSB-first，这是最高发的互通 bug |
| C3 | **坐标系手性** | `x` 向右、`y` 向上、`z`（层号）向屏幕外。「逆时针」定义为**从 +Z 向 −Z 俯视时的逆时针** | 屏幕坐标 `y` 向下会让同一段代码输出顺时针，两份实现互为镜像 |
| C4 | **光栅方向** | `q = y · 1024 + x`，即 **y 升序（底行优先）、x 升序** | 与图像光栅（顶行优先）相反，照抄图像代码会上下翻转 |
| C5 | **全局比特序号** | `i = 字节序号 × 8 + 位序号`，位序号按 C2 的 MSB-first | 与 C2 联动 |

### 2.3 常量

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `n` | 1024 | 层边长（`dimX = dimY`） |
| `L` | 1,048,576 | 每层比特数 = `n²` = 2²⁰ |
| `LAYER_BYTES` | 131,072 | 每层字节数 = `L / 8` = 128 KiB |
| `RING_COUNT` | 512 | 每层圈数 = `n / 2` |
| `SEG_COUNT` | 2048 | 每层等差段数 = `512 × 4` |
| `HEADER_SIZE` | 128 | 头部字节数 |
| `CHACHA_BLOCK` | 64 | ChaCha20 块字节数 |
| `BLOCKS_PER_LAYER` | 2048 | `131072 / 64` |
| `MAX_PAYLOAD` | 256 GiB | 32 位块计数器上限 `2³² × 64` |

## 3. 文件布局总览

```
偏移 0                                                              偏移 128
┌──────────────────────────────────────────────────────────────┬───────────────────────┐
│                        头部 header                            │      payload          │
│                       固定 128 字节                           │    origSize 字节       │
│  magic │ ver │ flags │ origSize │ layerCount │ dim │ nonce │  │  层0 │ 层1 │ … │ 层N-1 │
│                          …    │ DEK(32B) │ payload_tag(32B)  │                       │
└──────────────────────────────────────────────────────────────┴───────────────────────┘
```

- **总大小 = `origSize + 128` 字节，精确，无向上取整。**
- payload 由 `layerCount` 个变长层段顺序拼接而成。
- 第 `layer` 个层段的长度 = `min(origSize − layer × 131072, 131072)` 字节。
- 除最后一层外，所有层段长度都是 131,072 字节。

**层段长度推导（规范性）**：

```
layerBytes(layer) = min(origSize − layer × LAYER_BYTES, LAYER_BYTES)
layerBits(layer)  = layerBytes(layer) × 8          // 记作 m，秩压缩的模
layerCount        = ceil(origSize / LAYER_BYTES)   // origSize = 0 时为 0
```

### 4.2 `flags` 字节（偏移 5）逐位展开

| 位 | 权重 | 名称 | 规范值 | 含义 |
| --- | --- | --- | --- | --- |
| bit0 | 1 | `SPIRAL_CW` | `0` | 螺旋方向：`0` = 逆时针（规范），`1` = 顺时针 |
| bit1 | 2 | `BIT_LSB_FIRST` | `0` | 位序：`0` = MSB-first（规范，见 C2），`1` = LSB-first |
| bit2 | 4 | `KEYSTREAM_ON` | `1` | 密钥流：`0` = 关（**v1 禁止**），`1` = 开 |
| bit3 | 8 | `AFFINE_ON` | `1` | 仿射扫描：`0` = 纯光栅，`1` = 仿射（规范，见 §6） |
| bit4 | 16 | `RANK_COMPACT` | `1` | 秩压缩：`0` = 末层补满整层，`1` = 秩压缩（规范，见 §7） |
| bit5 | 32 | `COMPRESSED` | `0` | v1 保留，**必须为 0**；v2 用于每层压缩 |
| bit6 | 64 | reserved | `0` | 必须为 0 |
| bit7 | 128 | reserved | `0` | 必须为 0 |

**规范 profile 的 flags 值**：`bit2 + bit3 + bit4 = 4 + 8 + 16 = 28 = 0x1C`。

二进制展开：`0b0001_1100`

```
bit:   7  6  5  4  3  2  1  0
值:    0  0  0  1  1  1  0  0
              │  │  │  └── SPIRAL_CW    = 0  逆时针
              │  │  └───── BIT_LSB_FIRST = 0  MSB-first
              │  └──────── KEYSTREAM_ON  = 1  开
              └─────────── AFFINE_ON     = 1  开
```

**解码方的强制校验**：

```
(flags & 0xE3) == 0x00     // 0xE3 = 0b1110_0011 = bit0|bit1|bit5|bit6|bit7，这五位必须全 0
(flags & 0x1C) == 0x1C     // 0x1C = 0b0001_1100 = bit2|bit3|bit4，这三位必须全 1
```

两个掩码互斥且并集为 `0xFF`，因此等价于 `flags == 0x1C`；拆成两条是为了让错误信息能区分「有未支持的位置 1」与「必需位没置 1」。任一不满足即报「不支持的 profile」，**禁止**静默降级。

> **掩码算错的后果（实测核对得出）**：若把必零位掩码写成 `0xC3`（`= 0b1100_0011`，漏掉 bit5），则 `COMPRESSED` 位被置 1 的容器会通过校验，解码方按未压缩解析一段压缩数据，输出全是垃圾 —— 而 `payload_tag` 是在**去压缩之前还是之后**计算属于 v2 才定义的行为，v1 解码方无从判断。这类「掩码少一位」的缺陷不会让任何测试变红，只会让畸形输入静默通过。

### 4.3 关键字段的语义细节

**`origSize`（偏移 8..15）** —— 往返闭环的唯一保证。

末层几乎必然填不满，其填充比特在数学上是歧义的：解码方无法从 payload 本身判断哪些比特是数据、哪些是补齐。`origSize` 精确消除这个歧义。它同时决定：

- `layerCount`（冗余存储，用于交叉校验：解码方**必须**验证 `layerCount == ceil(origSize / 131072)`，不等则报头部损坏）；
- 每层的 `m`（秩压缩的模，见 §7）；
- 解码输出的截断位置。

**`file_nonce`（偏移 32..43）** —— 每文件必须重新随机生成。

ChaCha20 在「同一密钥 + 同一 nonce」下重用会构成 two-time pad：两个容器的 payload 异或即得两份明文的异或，可直接 crib-drag 破解。虽然本格式每文件的 DEK 也是随机的（双重保护），但仍**必须**每文件重新生成 nonce —— 否则一旦某个实现错误地复用了 DEK，就没有第二道防线。

**`dek`（偏移 64..95）** —— 每文件必须重新随机生成，**明文存储**。这是 §12 安全定性的根源。

### 4.4 `payload_tag` 的计算

```
1. 取头部 128 字节的副本，把偏移 96..127 这 32 字节全部置 0
2. data = 置零后的头部(128 B) ‖ payload(origSize B)
3. payload_tag = HMAC-SHA256(key = dek, data)
4. 把结果写入头部偏移 96..127
```

解码方按同样步骤重算并比对，**必须**用常量时间比较（避免时序侧信道——虽然本格式不提供机密性，但保留这个习惯没有成本）。不匹配时报「容器损坏或版本不符」，**禁止**输出任何还原数据。

注意：`data` 包含 `dek` 自身（位于头部 64..95）。这不构成安全问题，因为 `payload_tag` 本来就不提供认证（见 §12）。

## 5. 几何映射 I：分层与螺旋闭式

### 5.1 分层

```
layer = i >> 20            // i / 1048576，纯位移
s     = i & 0xFFFFF        // i mod 1048576
```

`L = 2²⁰` 是 2 的幂，因此分层是纯位运算，**禁止**用除法（在部分语言里会引入不必要的开销，且易与有符号右移的舍入行为混淆）。

### 5.2 螺旋的几何定义

- 起点：第 `k` 圈的**左下角** `(k, k)`（`y` 向上，故 `k` 是该圈最小的 `y`）。
- 方向：**逆时针**（从 +Z 俯视）。按 C3/C4 的坐标系，从左下角逆时针行进的边序为：**下边 → 右边 → 上边 → 左边**。
- 圈数：`k = 0 .. 511`，共 512 圈。第 `k` 圈边长 `m = 1024 − 2k`，取值 `1024, 1022, …, 4, 2`。

**逆时针的自洽性核对**（避免手性搞反）：在 `x` 右、`y` 上的坐标系里，逆时针 = 极角递增。左下角 `(k,k)` 相对圈中心的极角约 225°，递增依次经过 270°（下边中点）、315°（右下角）、0°（右边中点）。因此从左下角出发先沿**下边向右**，再沿**右边向上**，这与「时钟指针 3→6→9→12 的反向」一致 ✓。

### 5.3 圈基址

前 `k` 圈（`0 .. k−1`）占用的格子总数：

```
s0(k) = Σ_{j=0}^{k−1} (4·m_j − 4)  其中 m_j = n − 2j
      = Σ_{j=0}^{k−1} (4n − 8j − 4)
      = 4k(n − k)
```

**验算**：
- `s0(0) = 0` ✓
- `s0(1) = 4 · 1 · 1023 = 4092`，而最外圈格子数 `= 4 × 1024 − 4 = 4092` ✓
- `s0(511) = 4 · 511 · 513 = 1,048,572`，最内圈 `m = 2`，格子数 `4 × 2 − 4 = 4`，末格序号 `1,048,575 = L − 1` ✓

### 5.4 覆盖完备性（规范性证明）

**命题**：`k = 0..511` 的 512 圈恰好覆盖 1024×1024 的全部 1,048,576 个格子，无遗漏、无重复。

**证明**：第 `k` 圈覆盖边界框 `[k, k+m−1] × [k, k+m−1]` 的**周界**，`m = n − 2k`。周界格子数 `= 4m − 4`（`m ≥ 2` 时成立；`m = 2` 时退化为 2×2 实心块，`4 × 2 − 4 = 4` 仍正确）。

```
Σ_{k=0}^{511} (4m − 4) = Σ_{k=0}^{511} (4(1024 − 2k) − 4)
                       = Σ_{k=0}^{511} (4092 − 8k)
                       = 512 × 4092 − 8 × (511 × 512 / 2)
                       = 2,095,104 − 8 × 130,816
                       = 2,095,104 − 1,046,528
                       = 1,048,576  = n²  ∎
```

各圈的边界框互不相交（第 `k` 圈在 `[k, n−1−k]²` 的周界，第 `k+1` 圈在 `[k+1, n−2−k]²` 的周界，前者严格包含后者的内部），故无重复。计数与格数相等且无重复 ⇒ 无遗漏。∎

### 5.5 正向闭式：`s → (x, y)`

```
输入: s ∈ [0, L)
n = 1024

1. 定圈:  k = floor( (n − sqrt(n² − s)) / 2 )
2. 校正:  while (4·(k+1)·(n−k−1) ≤ s) k++          // 至多 1 次
          while (k > 0 and 4·k·(n−k) > s)  k--      // 至多 1 次
3. 参数:  m  = n − 2k
          s0 = 4·k·(n − k)
          t  = s − s0                                // 0 ≤ t < 4m − 4
4. 拆边:
   t < m−1        →  x = k + t,                       y = k                     // 下边
   t < 2(m−1)     →  x = k + m − 1,                   y = k + (t − (m−1))       // 右边
   t < 3(m−1)     →  x = k + m − 1 − (t − 2(m−1)),    y = k + m − 1             // 上边
   否则           →  x = k,                            y = k + m − 1 − (t − 3(m−1)) // 左边
```

**第 1 步的推导**：要求最小的 `k` 使 `s0(k) ≤ s`，即 `4k(n−k) ≤ s`。整理得 `k² − nk + s/4 ≥ 0`，两根为 `(n ± sqrt(n² − s)) / 2`，取小根即得。

`sqrt` 的精度：`n² = 1,048,576`，被开方数在 `[0, 2²⁰]` 内，float64 对 2⁵³ 以内的整数开方正确舍入，故 `floor` 安全。**但第 2 步的整数校正仍然必须保留** —— 它是 O(1) 的，且能吸收任何跨平台的浮点舍入差异。省略校正是「本地能跑、换平台就错」的典型来源。

### 5.6 逆向闭式：`(x, y) → s`

```
输入: x, y ∈ [0, n)

1. 定圈:  k = min(x, y, n−1−x, n−1−y)
2. 参数:  m  = n − 2k
          s0 = 4·k·(n − k)
3. 判边并求 s:
   下边  (y == k       and k ≤ x ≤ k+m−2)  →  s = s0 + (x − k)
   右边  (x == k+m−1   and k ≤ y ≤ k+m−2)  →  s = s0 + (m−1) + (y − k)
   上边  (y == k+m−1   and k+1 ≤ x ≤ k+m−1) →  s = s0 + 2(m−1) + (k+m−1 − x)
   左边  (x == k       and k+1 ≤ y ≤ k+m−1) →  s = s0 + 3(m−1) + (k+m−1 − y)
```

**四个角的归属核对**（判边条件必须互斥且完备）：

| 角 | 坐标 | 命中分支 | `t` | `s` |
| --- | --- | --- | --- | --- |
| 左下（起点） | `(k, k)` | 下边（`x = k ≤ k+m−2`，因 `m ≥ 2`） | 0 | `s0` |
| 右下 | `(k+m−1, k)` | 右边（下边要求 `x ≤ k+m−2`，不满足） | 0 | `s0 + (m−1)` |
| 右上 | `(k+m−1, k+m−1)` | 上边（右边要求 `y ≤ k+m−2`，不满足） | 0 | `s0 + 2(m−1)` |
| 左上 | `(k, k+m−1)` | 左边（上边要求 `x ≥ k+1`，不满足） | 0 | `s0 + 3(m−1)` |

**`m = 2` 退化核对**（`k = 511`，最内圈）：四边各 1 格，覆盖 `{(511,511), (512,511), (512,512), (511,512)}`，`s = s0 .. s0+3`，正好是 2×2 实心块 ✓。

### 5.7 关键性能性质：分段等差

四条边的 `(x, y)` 都是参数 `t` 的线性函数，因此 `q = y·1024 + x` 在每条边上是等差数列：

| 边 | `q` 步进 | 段长 |
| --- | --- | --- |
| 下边 | `+1` | `m − 1` |
| 右边 | `+1024` | `m − 1` |
| 上边 | `−1` | `m − 1` |
| 左边 | `−1024` | `m − 1` |

由于 §6 的仿射变换也是线性的，`r = (a·q + b) mod 2²⁰` 在每条边上同样是等差数列：

| 边 | `r` 步进（mod 2²⁰） |
| --- | --- |
| 下边 | `+a` |
| 右边 | `+1024a` |
| 上边 | `−a` |
| 左边 | `−1024a` |

**结论**：一整层的映射可由 `512 圈 × 4 边 = 2048` 个 `(起点, 公差, 长度)` 三元组完整描述，段内只需加法递推。**没有 `sqrt`、没有除法、不需要 100 万条目的置换表**（那会占 4 MB 并摧毁 cache 局部性）。

`sqrt` 闭式（§5.5）只在「随机访问单个原始比特」时才需要，那条路径是 O(1) 且冷。

## 6. 几何映射 II：仿射扫描

### 6.1 为什么需要它

**纯螺旋 + 纯光栅存储会泄露 50% 的原文邻接结构。** 这不是参数没调好，而是一般性结论：

只要存储扫描在 `x` 方向连续（`q = y·n + x`），螺旋的两条**水平边**就必然落在 `|Δq| = 1` 的位置上 —— 与起点选哪个角、顺时针还是逆时针、`y` 朝上还是朝下、从哪一圈开始，全都无关。

对 `n = 1024` 求和，四类边各占**正好 25%**：

```
每类格子数 = Σ_{k=0}^{511} (m − 1) = Σ_{k=0}^{511} (1023 − 2k)
           = 512 × 1023 − 2 × (511 × 512 / 2)
           = 523,776 − 261,632
           = 262,144  = L / 4  ✓
```

| 边 | `s` 步进 | `q` 步进 | 效果 |
| --- | --- | --- | --- |
| 下边 | `+1` | **`+1`** | **恒等** —— 原文逐位照抄 |
| 上边 | `+1` | **`−1`** | 位序反转 —— 结构极明显 |
| 右边 | `+1` | `+1024` | 跨行打散 ✓ |
| 左边 | `+1` | `−1024` | 跨行打散 ✓ |

**最外圈的具体后果**：下边覆盖 `s = 0..1022 → q = 0..1022`，紧接着右边第一格 `s = 1023 → q = 1023`。所以 `s = 0..1023` 全部恒等映射，即 **payload 的前 128 字节 = 原文件的前 128 字节，逐字节相同**。任何魔数嗅探器都能立刻识别。

### 6.2 变换定义

```
r = (a · q + b) mod 2²⁰
```

其中：

- `a ∈ [2¹⁹, 2²⁰)`，**必须为奇数**（奇数 ⇒ 与 `2²⁰` 互素 ⇒ 双射）
- `b ∈ [0, 2²⁰)`
- `a`、`b` 由 DEK 与 file_nonce 派生（§11），**每文件不同**

**逆变换**：

```
q = (a_inv · ((r − b) mod 2²⁰)) mod 2²⁰
其中 a_inv = a⁻¹ mod 2²⁰
```

`(r − b)` 必须先取模到 `[0, 2²⁰)` 再乘，否则负数在部分语言里会得到错误的取模结果。

### 6.3 散射效果

代入 §5.7 的步进：

| 边 | `r` 步进 | 数值范围 |
| --- | --- | --- |
| 下边 / 上边 | `±a` | `a ≥ 524,289` |
| 右边 / 左边 | `±1024a mod 2²⁰` = `±1024 · (a mod 1024)` | `a mod 1024` 为奇数 ∈ `[1, 1023]`，故步进 ∈ `{1024, 3072, …, 1047552}` |

四类边的 `|Δr|` 全部 ≥ 1024。段边界（每层 2048 处）的 `Δr` 是任意值，占比 `2048 / 1048576 = 0.195%`。

因此判据 2（§13）的「`|Δ| = 1` 占比 ≤ 1%」在满层上以 20 倍余量满足。

### 6.4 `a` 的取值范围为什么必须收窄

若直接令 `a = HKDF输出 | 1`（取满 `[1, 2²⁰)`），则 `a < 2¹⁰` 的概率是 `2¹⁰ / 2²⁰ = 1/1024`。此时下边步进 `a` 很小，散射退化。1/1024 的文件会静默地弱于其余文件 —— 这种「大多数时候对、偶尔不对」的缺陷最难查。

规范做法（§11）把 `a` 强制映射到 `[2¹⁹, 2²⁰)`，**结构上排除**小 `a`，而不是靠概率。

## 7. 几何映射 III：秩压缩

### 7.1 为什么需要它

仿射 `r` 是 `[0, 2²⁰)` 上的满射。若末层只有 `m < L` 个有效比特，它们会被散射到整个 `[0, 2²⁰)` 区间里 —— 要取回就必须写满整层 131,072 字节。

后果：**一个 1 字节的文件会膨胀成 128 KiB**。这违背 §1.1 的目标 4。

### 7.2 上一版方案的更正

> **显式更正**：设计讨论阶段曾提出「末层不做仿射散射，直接按填充序 `s` 紧凑存储」。该方案有两个缺陷，本版**废弃**：
>
> 1. 末层的存储序号 `r' = s`，即**末层完全没有几何置换**，只是原文异或密钥流。对于小于 128 KiB 的文件（占绝大多数），整个「三维映射」名存实亡。
> 2. 满层与末层走两条不同的几何代码路径。这种「最后一块特殊处理」是互通 bug 的高发区，也让判据 2 只能对满层成立。
>
> 现改为**秩压缩**，它对满层退化为恒等，因此**全部层共用一条代码路径**。

### 7.3 定义

设某层的有效比特数为 `m`（`1 ≤ m ≤ L`），该层被填充的格子是 `s = 0 .. m−1`。经螺旋与仿射后得到 `m` 个互异的散射序号，构成集合：

```
R = { r(s) : s ∈ [0, m) }     |R| = m
```

（互异性由「螺旋是单射」+「仿射在互素条件下是单射」保证。）

**秩压缩**定义为：

```
r' = rank(r) = |{ r'' ∈ R : r'' < r }|
```

这是 `R → [0, m)` 的双射。层内以 `r'` 为存储序号，打包成 `ceil(m / 8)` 字节落盘。

### 7.4 满层退化

`m = L = 2²⁰` 时 `R = [0, 2²⁰)` 是全集，故 `rank(r) = r`。**秩压缩在满层上严格退化为恒等映射**，与纯仿射的输出一字节不差。

因此实现**可以**（且**应当**）用单个分支跳过满层的秩计算：

```
if (m == L)  r' = r                      // 快路径，跳过位图
else         r' = rank(r)                 // 通用路径
```

这是**性能优化**而非语义分支 —— 两条路径必须产生相同结果，判据 12（§13）专门守这一点。

### 7.5 秩的高效计算

**编码侧**（已知全部 `R`，求每个元素的秩）。设机器字宽 `w` 位（32 或 64）：

```
1. 分配位图 B[2²⁰ 位] = 128 KiB，清零
2. 遍历 s = 0..m−1，算出 r(s)，置位 B[r] = 1
3. 构建字级前缀和 W[2²⁰ / w]，W[j] = Σ_{i<j} popcount(B[i])，并额外存末项 W[2²⁰/w] = m
4. rank(r) = W[r >> log₂w] + popcount( B[r >> log₂w] & ((1 << (r mod w)) − 1) )
```

每次查询 O(1)。内存开销随字宽而变：

| 字宽 `w` | 位图 | 前缀和（u32 项） | 合计 |
| --- | --- | --- | --- |
| 64 | 128 KiB | 16,385 × 4 B ≈ 64 KiB | ≈ 192 KiB |
| **32**（JS `Uint32Array` 的自然选择） | 128 KiB | 32,769 × 4 B ≈ 128 KiB | **≈ 256 KiB** |

两者都可跨层复用。步骤 3 的末项 `W[2²⁰/w]` 必须等于 `m` —— 这是一条免费的自检：不等就说明位图置位次数与 `m` 不符，即散射不是双射。Node 实现把它作为 `RANK_COUNT` 硬错误抛出。

**解码侧**：

解码**不需要**秩的反函数。解码方按填充序 `s = 0 .. m−1` 遍历，正向算出 `r(s)`，再查 `r' = rank(r)`，然后读 `O[r']` 写回 `S[s]`。因此解码侧复用与编码侧完全相同的 `rank()` 查询，只需先重建位图：

```
1. 重建同一个位图 B 与前缀和 W
   （解码方知道 m 与全部几何参数，按 §9.3 的等差段遍历 s = 0..m−1 即可）
2. 遍历 s = 0..m−1：r = affine(s)，r' = rank(r)，S[s] = O[r']
```

`rank` 的反函数 `select`（给定 `r'` 求 `r`）**不是本格式所需** —— 它只在「按存储序遍历」的解码写法里才用得上，而那种写法没有好处：它需要额外的二分查找与位扫描，且破坏 §5.7 等差段的加法递推。本规格**不要求**实现 `select`。

**注意**：解码侧必须**重建**位图，不能从 payload 推断。重建成本是每层 O(m) 次加法递推（走 §5.7 的等差快路径），相对 payload 本身的 O(m) 处理是常数倍开销。且只有末层需要重建 —— 满层走 §7.4 的恒等退化，跳过整个位图。

### 7.6 秩压缩与仿射的必要性关系

两者不可互相替代：

- 只有仿射、没有秩压缩 ⇒ 末层必须补满 128 KiB，体积膨胀。
- 只有秩压缩、没有仿射（即按光栅 `q` 排序）⇒ 下边的格子既有连续的 `s` 又有连续的 `q`，其秩也连续 ⇒ **恒等邻接泄露原样回归**。

## 8. 密钥流

### 8.1 算法与参数

| 项 | 规范值 |
| --- | --- |
| 算法 | ChaCha20（RFC 8439） |
| 密钥 | `dek`（头部偏移 64..95，32 字节） |
| nonce | `file_nonce`（头部偏移 32..43，12 字节） |
| 块大小 | 64 字节 |
| 计数器 | 32 位，**第 `layer` 层的计数器基址 = `layer × 2048`** |

### 8.2 为什么计数器基址按层乘 2048

`131072 / 64 = 2048`，即一个满层恰好消耗 2048 个块。以 `layer × 2048` 为基址保证：

1. **各层密钥流互不重叠** —— 第 `layer` 层最多消耗 2048 块，正好不与第 `layer + 1` 层的基址相撞；
2. **任意层可独立解密** —— 直接从 `layer × 2048` 起算即可，无需先解前面的层；
3. **上限充足** —— 32 位计数器 ⇒ `2³² / 2048 = 2,097,152` 层 ⇒ `2,097,152 × 128 KiB = 256 GiB` payload。

末层实际消耗的块数少于 2048（因为长度不足 131,072 字节），预留的空隙不造成问题。

### 8.3 与 OpenSSL / Node 的绑定差异

RFC 8439 的 ChaCha20 参数是「12 字节 nonce + 32 位计数器」。OpenSSL（因而 Node 的 `crypto.createCipheriv('chacha20', key, iv)`）要求 **16 字节 IV**，其布局为：

```
IV = 计数器 u32 LE (4 B) ‖ nonce (12 B)
```

各栈绑定方式不同，本文只规范 RFC 8439 层面的参数，**不**规范具体 API 的 IV 拼装方式。实现必须在自己的 README 里写明所用绑定，并用黄金向量（§15）交叉验证。

### 8.4 末层填充与密钥流泄露

末层的有效比特数为 `m`，落盘 `ceil(m/8)` 字节。最后一个字节可能只有一部分比特是数据，其余为 0 填充。这些填充位异或密钥流后等于**裸露的密钥流比特**，且其位置可由头部的 `origSize` 明文算出。

- 用 ChaCha20 这类密码学安全 CSPRNG 时，泄露部分输出**不会**帮助恢复密钥或其他位置的输出，因此无害。
- 若实现换成 LCG / xorshift / xoshiro 这类小状态 PRNG，攻击者可从泄露段反推内部状态，进而恢复**整个**密钥流。**禁止**为此格式使用非密码学安全的 PRNG。

## 9. 编码算法（规范性）

### 9.1 顶层流程

```
encode(inputPath, outputPath):
  1. origSize = 输入文件字节数
  2. layerCount = ceil(origSize / LAYER_BYTES)          // origSize = 0 → 0
  3. dek        = CSPRNG(32)
  4. file_nonce = CSPRNG(12)
  5. (a, b)     = deriveAffine(dek, file_nonce)          // §11
  6. a_inv      = modInverse(a, 2²⁰)                     // 编码侧不需要，但一并算出供自检
  7. 构造 128 字节头部，payload_tag 位置暂置 0
  8. for layer in 0 .. layerCount−1:
        seg = encodeLayer(layer, m = layerBits(layer))
        追加 seg 到 payload
  9. payload_tag = HMAC-SHA256(dek, 头部(tag 置零) ‖ payload)
 10. 写入头部偏移 96..127
 11. 输出 = 头部 ‖ payload
```

### 9.2 单层编码

```
encodeLayer(layer, m):
  // --- 阶段 A：读入并按填充序展开 ---
  S = 长度为 m 的比特数组
  从输入文件偏移 layer × LAYER_BYTES 读 ceil(m/8) 字节
  按 C2（MSB-first）展开为 S[0 .. m−1]
  // 末字节若含填充位，展开后丢弃超出 m 的部分

  // --- 阶段 B：几何散射到层缓冲 ---
  O = 长度为 L 的比特数组，清零                     // 满层时用到全部；末层只用到 [0, m)
  if (m == L):
      走满层快路径：遍历 2048 个等差段
        for 每段 (s_start, r_start, r_step, len):
            for j in 0 .. len−1:
                O[r_start + j·r_step mod 2²⁰] = S[s_start + j]
  else:
      走秩压缩路径（§7.5）：
        1. 遍历 2048 段中 s < m 的部分，算出每个 s 的 r(s)，置位图 B[r(s)] = 1
        2. 构建字级前缀和 W
        3. 再次遍历，r' = rank(r(s))，置 O[r'] = S[s]

  // --- 阶段 C：打包 ---
  P = ceil(m / 8) 字节
  按 C2（MSB-first）把 O[0 .. m−1] 打包进 P
  // 末字节的低位填充 0

  // --- 阶段 D：密钥流 ---
  ks = ChaCha20(dek, file_nonce, counter = layer × 2048) 的前 P 字节
  P = P XOR ks

  return P
```

### 9.3 等差段的构造

由 §5.3、§5.5、§6.2，第 `k` 圈（`m = 1024 − 2k`）的四段为：

| 边 | `s` 起点 | 首格 `(x, y)` | 首个 `q` | 首个 `r` | `r` 公差 | 段长 |
| --- | --- | --- | --- | --- | --- | --- |
| 下边 | `s0` | `(k, k)` | `1024k + k` | `(a·(1025k) + b) mod 2²⁰` | `+a` | `m − 1` |
| 右边 | `s0 + (m−1)` | `(k+m−1, k)` | `1024k + k+m−1` | 同上式代入 | `+1024a` | `m − 1` |
| 上边 | `s0 + 2(m−1)` | `(k+m−1, k+m−1)` | `1024(k+m−1) + k+m−1` | 同上式代入 | `−a` | `m − 1` |
| 左边 | `s0 + 3(m−1)` | `(k, k+m−1)` | `1024(k+m−1) + k` | 同上式代入 | `−1024a` | `m − 1` |

其中 `s0 = 4k(1024 − k)`。公差一律先 `mod 2²⁰` 归一到 `[0, 2²⁰)`，递推时 `r = (r + step) mod 2²⁰`。

**末层截断**：若某段的 `s` 区间越过 `m`，只处理 `s < m` 的部分，段长按 `min(len, m − s_start)` 截断；`s_start ≥ m` 的段整段跳过。

## 10. 解码算法（规范性）

### 10.1 顶层流程

```
decode(inputPath, outputPath):
  1. 读头部 128 字节；文件长度 < 128 → 报「文件过短」
  2. 校验 magic == "BT3D"、version == 1、reserved0/1 == 0、reserved2 全 0
  3. 校验 flags：(flags & 0xE3) == 0 且 (flags & 0x1C) == 0x1C，否则报「不支持的 profile」
  4. 校验 dimX == dimY == 1024，否则报「不支持的几何」
  5. 读 origSize、layerCount；校验 layerCount == ceil(origSize / 131072)，否则报「头部损坏」
  6. 校验 文件长度 == origSize + 128，否则报「文件截断或有多余数据」
  7. 取 dek、file_nonce；派生 (a, b) 与 a_inv
  8. 重算 payload_tag 并**常量时间比较**；不匹配 → 报「容器损坏」，禁止输出任何数据
  9. for layer in 0 .. layerCount−1:
        读该层段（长度 layerBytes(layer)），decodeLayer，追加到输出
 10. 输出长度必须 == origSize（自检）
```

### 10.2 单层解码

```
decodeLayer(layer, segBytes):                 // segBytes = layerBytes(layer) = ceil(m/8)，m = segBytes × 8
  // --- 阶段 D'：去密钥流 ---
  ks = ChaCha20(dek, file_nonce, counter = layer × 2048) 的前 segBytes 字节
  P  = 从 payload 偏移 128 + Σ_{j<layer} layerBytes(j) 处读入的 segBytes 字节
  P  = P XOR ks

  // --- 阶段 C'：解包 ---
  O = 长度 L 的比特数组，清零
  按 C2 把 P 展开到 O[0 .. m−1]

  // --- 阶段 B'：几何聚集 ---
  S = 长度为 m 的比特数组
  if (m == L):
      遍历 2048 段：S[s_start + j] = O[(r_start + j·r_step) mod 2²⁰]
  else:
      重建位图 B 与前缀和 W（§7.5 解码侧）
      遍历 s = 0..m−1：r = affine(s)，r' = rankInv 查表，S[s] = O[r']

  // --- 阶段 A'：打包 ---
  按 C2 把 S[0 .. m−1] 打包成 m/8 字节（m 必为 8 的倍数，因为 m = 字节数 × 8）
  return 该结果
```

**注**：`m` 恒为 8 的倍数（`m = layerBytes × 8`），因此单层输出永远是整字节，阶段 A' 无需处理位截断。位截断只发生在 §9.2 阶段 A 读入末字节的填充位时。

## 11. 参数派生

### 11.1 规范流程

```
HKDF-Expand-Only 太弱，用完整 HKDF-SHA256：

ikm  = dek                     (32 B)
salt = file_nonce              (12 B)

okm_a = HKDF-SHA256(ikm, salt, info = "BT3D-v1-scan-a", len = 32)
okm_b = HKDF-SHA256(ikm, salt, info = "BT3D-v1-scan-b", len = 32)

t = LE64(okm_a[0..7]) mod 2¹⁹
a = (2¹⁹ + t) | 1                          // a ∈ [2¹⁹, 2²⁰)，恒为奇数

b = LE64(okm_b[0..7]) mod 2²⁰              // b ∈ [0, 2²⁰)
```

`info` 字符串**必须**逐字节使用上表字面值（含 `BT3D-v1-` 前缀），用于域分隔，防止 `a` 与 `b` 的派生路径重叠。

### 11.2 模逆 `a_inv = a⁻¹ mod 2²⁰`

`a` 为奇数 ⇒ `gcd(a, 2²⁰) = 1` ⇒ 逆元存在且唯一。

**牛顿迭代 / Hensel 提升**：若 `x ≡ a⁻¹ (mod 2ᵏ)`，则 `x' = x(2 − a·x) ≡ a⁻¹ (mod 2²ᵏ)` —— **每轮精度翻倍**。从 `k = 1` 提升到 `k ≥ 20` 的轮数是 `⌈log₂ 20⌉ = 5`（精度轨迹 1 → 2 → 4 → 8 → 16 → 32）。

```
x = 1                                        // a 为奇数 ⇒ a·x ≡ 1 (mod 2)
repeat 5 times:
    x = (x · (2 − a · x)) mod 2²⁰            // 每轮末尾必须立刻归一
// 结束时 x = a⁻¹ mod 2²⁰
```

> **轮数写错的后果**：按「每轮 +1 位精度」的直觉写 19 轮不会出错（多算的轮次是幂等的），但按「每轮翻倍」写 4 轮会**静默产出错误的逆元** —— 精度只到 mod 2¹⁶，解码侧 `q = a_inv·(r−b)` 会算出错误的光栅序号，进而还原出完全错乱的字节。这个错误在往返测试里必然暴露，但根因藏在 5 与 4 的差别里，极难定位。判据 13 用 `a · a_inv ≡ 1 (mod 2²⁰)` 直接守这一条。

**溢出警告（规范性）**：即使每轮归一，中间积仍会超出窄类型。设 `a, x < 2²⁰`：

| 中间量 | 上界 | float64（精确整数 < 2⁵³） | u64 |
| --- | --- | --- | --- |
| `a · x` | `2⁴⁰` | ✅ | ✅ |
| `2 − a·x` | 约 `−2⁴⁰` | ✅ | 需 wrapping |
| `x · (2 − a·x)` | 约 `2⁶⁰` | ❌ **超出 2⁵³** | ✅ `< 2⁶⁴` |

- **JavaScript 必须全程用 `BigInt`**，否则最后一行的乘积会丢精度，得到一个看似合理但错误的逆元；
- Rust / Go / C 可用 `u64` 配合 wrapping 乘法；
- 每轮结束后**必须**立刻 `mod 2²⁰` 归一，否则下一轮溢出。

也可用扩展欧几里得算法，同样需要宽整数。

### 11.3 派生的确定性

`(a, b, a_inv)` 完全由 `(dek, file_nonce)` 决定，不含任何运行时随机性。因此：

- 编码方与解码方各自独立派生，结果必须逐位相同（判据 13 守这一点）；
- 黄金向量（§15）可以固定 `dek` 与 `file_nonce`，从而得到完全可复现的 payload。

## 12. 安全定性

**本节必须被任何使用者读到。它不是免责声明，而是格式的实际能力边界。**

### 12.1 提供的保护

| 威胁 | 是否防住 | 机制 |
| --- | --- | --- |
| `file` / 魔数嗅探 | ✅ | payload 是 ChaCha20 输出，无可识别结构 |
| hex 编辑器肉眼判读 | ✅ | 同上 |
| 自动内容分类 / 索引器 | ✅ | 同上 |
| 压缩率指纹（判据 3） | ✅ | 密钥流使 payload 不可压 |
| 1 比特占比指纹（判据 4） | ✅ | 密钥流使占比趋近 50% |
| 原文公共子串（判据 1） | ✅ | 仿射散射 + 密钥流 |
| 意外损坏（截断、位翻转、传输错误） | ✅ | `payload_tag` |
| 同内容文件产生相同容器 | ✅ | DEK 与 nonce 每文件随机（判据 8） |

### 12.2 不提供的保护

| 威胁 | 是否防住 | 原因 |
| --- | --- | --- |
| **任何持有容器文件的人读取原文** | ❌ | DEK 明文存于头部偏移 64..95。读出 32 字节即可完整解密。 |
| 蓄意伪造 / 篡改 | ❌ | `payload_tag` 的 HMAC 密钥就是 DEK，攻击者可对任意修改后的 payload 重算合法 tag。 |
| 知道本规格的人还原 | ❌ | 规格是公开的，DEK 也在文件里，还原是纯机械操作。 |
| 元数据泄露 | ❌ | `origSize` 明文存于头部。文件大小本身常足以识别内容（如固定大小的数据库快照）。 |

### 12.3 定量表述

> **本格式在密码学意义下的机密性强度为 0 bit。**
>
> 它提供的是**混淆（obfuscation）**，不是**加密（encryption）**。二者区别在于：加密的安全性依赖密钥的保密性；本格式的密钥与密文同处一个文件，因此安全性依赖的是「攻击者没有拿到这个文件」—— 而一旦攻击者拿到了文件，格式就不再提供任何保护。

### 12.4 为什么仍然选择这个挡位

设计讨论中曾评估过三个挡位：

| 挡位 | DEK 存放 | 机密性 | 「可恢复」的条件 |
| --- | --- | --- | --- |
| A · 纯几何 | 无 DEK | 0 bit | 无条件 |
| **B · 明文 DEK（本格式）** | 头部偏移 64..95 | **0 bit** | **无条件** |
| C · 口令包裹 DEK | 头部，被口令派生的 KEK 加密 | 依赖口令强度 | 需记得口令 |

选 B 而非 C 的理由是「可恢复」**无条件成立** —— 不存在忘口令导致数据永久丢失的风险。
选 B 而非 A 的理由是 B 的 DEK 每文件随机，因而仿射参数 `(a, b)` 与密钥流也每文件随机，使容器之间无法互相对拍，且修掉了 A 挡下的三个指纹泄露（判据 1、3、4）。

### 12.5 升级到挡位 C 的路径

本格式的头部布局已为升级预留：偏移 44..63 的 20 字节 `reserved2` 可容纳 KDF 参数（`m` / `t` / `p` 各 u32 = 12 字节）与 8 字节余量。升级步骤：

1. `version` 改为 `2`；
2. 新增 `kdf_salt`（占用 `reserved2` 的前 16 字节）；
3. `KEK = Argon2id(口令, kdf_salt, m, t, p)`；
4. 头部偏移 64..95 由「明文 DEK」改为「XChaCha20-Poly1305(KEK, DEK)」的 32 字节密文 —— **但这样没有认证标签空间**，需要把 `payload_tag` 从 32 字节缩到 16 字节以腾出 16 字节给 wrap tag；
5. `flags` 新增 bit6 表示「DEK 已包裹」。

升级后 §6 的仿射散射与 §7 的秩压缩**从装饰变为承重墙** —— 因为此时攻击者即使拿到容器也无法直接读出 DEK，几何结构成为他必须猜测的第二道关卡。这是本格式坚持保留仿射与秩压缩（而非退化成纯密钥流）的主要工程理由。

**编号沿革**：判据 1~11 是设计阶段确定的原始 11 条，编号**冻结不变**（各栈测试脚本与 README 都按此编号引用）。判据 12、13 是规格定稿时新增（守 §7 秩压缩与 §11 参数派生）；判据 14、15 是 Node 实现落地时新增（守 §8.3 的 ChaCha20 绑定与 §4.1 的头部偏移）。**当前总计 15 条**，后续只追加、不重排。

判据 14 与 15 都是**跨栈互通专用**：它们断言的是与外部权威（RFC 8439、本规格 §4.1）的一致性，而不是实现自身的自洽性。判据 5 那类自洽测试永远抓不到「IV 拼装顺序不同」或「字段偏移差 2 字节」—— 这两种错误在本实现内部完全自洽，只有在与另一语言的实现对拍时才暴露，而那时数据可能已经写出去了。

### 13.2 判据 5 的五个边界文件

| 用例 | 大小 | 为什么是这个数 |
| --- | --- | --- |
| E1 | 0 B | `layerCount = 0`，payload 长度 0，头部仍需完整 |
| E2 | 1 B | 单层，`m = 8`，秩压缩的极小模 |
| E3 | **131,072 B** | 正好一整层。**`layerCount` 必须是 1 而不是 2** —— off-by-one 最高发点 |
| E4 | 131,073 B | 2 层，第二层 `m = 8`，跨层进位 |
| E5 | **38,797,313 B**（= 37 MiB + 1 B）随机 | 296 个满层 + 1 个 `m = 8` 的末层，覆盖大文件下的末层路径 |

> **E5 的取值踩过一次坑，记录下来以防复发。**
>
> 设计阶段原本写的是「37 MiB 随机文件，非整层倍数」。实算发现 `37 × 1024 × 1024 = 38,797,312`，而 `38,797,312 / 131,072 = 296` **恰好整除** —— 因为 1 MiB = 8 × 128 KiB，所以**任何整数 MiB 都是 128 KiB 的整数倍**。
>
> 若照原计划用 37 MiB，这个用例会全绿通过，但它**根本没走到末层代码路径**：`layerCount = 296`，全部是满层，秩压缩分支一次都没执行。这是典型的「判据假绿」—— 用例名字声称在测末层，实际在重测满层。
>
> **规范化写法**：凡是要触发末层的用例，大小必须显式写成 `k × 131072 + r`（`0 < r < 131072`）的形式，禁止用「N MiB」这类看起来随意、实际必然整除的表述。本表的 E3 / E4 / E5 都符合这个写法。

### 13.3 判据 2 为什么只适用于满层

末层的 `m` 可能很小（E2、E4 的 `m = 8`）。任何 `[0, m)` 上的置换，其 `|Δ| = 1` 的概率约为 `2/m`；`m = 8` 时约 25%，必然超过 1% 阈值。

这不是实现缺陷，而是**该判据在小 `m` 下不具备区分力**。因此：

- 满层：断言 `|Δ| = 1` 占比 ≤ 1% 且中位数 ≥ 256；
- 末层：**只报告实测值，不设阈值**，并在文档中说明理由。

对末层真正有区分力的是判据 1（公共子串）—— 它在任意大小下都成立。

### 13.4 判据为什么不能只跑第 5 条

**往返测试（判据 5）对判据 1~4 那四类缺陷全是假绿的**：几何映射算错了但编解码同源出错，照样能完美还原。混淆容器必须额外有「打在缺陷可见的那一层」的判据。

同理：

- 判据 10 抓「快路径段起点算错」—— 快慢路径同源时判据 5 绿；
- 判据 11 抓「`a` 意外为偶数」—— 此时判据 5 会红，但报错位置完全指不到根因；
- 判据 12 抓「秩压缩在满层没退化成恒等」—— 若快路径分支写错，判据 5 仍可能绿（因为编解码都用同一条错分支）；
- 判据 13 抓「模逆算错」。注意 `a_inv` 并**不**被流式解码路径使用（解码按 `s` 顺序正向遍历段表，只需 `a`、`b`），它服务于随机访问路径；因此模逆算错时判据 5 依然是绿的，只有 `a · a_inv ≡ 1 (mod 2²⁰)` 这条不依赖任何路径的直接断言能抓到；
- 判据 14、15 抓「与外部权威不一致」—— RFC 8439 的 IV 拼装顺序、§4.1 的字段偏移。这两类错误在本实现内部完全自洽，判据 5 与判据 10 都会绿。

§16.3 的缺陷注入实测给出了直接证据：**四个注入缺陷（D1 缺 keystream 的两种、D5 位序、D6 边序）全部往返一致**。

### 13.5 判据 3 的特殊地位

判据 3（压缩率）是**唯一能客观区分「转置」与「真混淆」的数**。置换不改变香农熵，因此任何纯几何方案在文本输入上都能被 `zstd` 压到约 0.30；只有叠加了密钥流，压缩比才会升到 0.98 以上。

若某个实现只做了螺旋+仿射而漏掉 ChaCha20，判据 1、5、6、7 可能全绿，只有判据 3 和判据 4 会红。

## 14. 实现注意事项与已知陷阱

### 14.1 数值溢出

| 表达式 | 上界 | float64 安全？ | u64 安全？ | 规范做法 |
| --- | --- | --- | --- | --- |
| `a20 · q`（`a20 = a mod 2²⁰`） | `2⁴⁰` | ✅ `< 2⁵³` | ✅ | 先把 `a` 归一到 20 位再乘 |
| `a · q`（`a` 未归一） | `2⁸⁴` | ❌ | ❌ | **禁止**，必须先归一 |
| `a · x`（牛顿迭代中间积） | `2⁴⁰` | ✅ | ✅ | 每轮后立刻 `mod 2²⁰` |
| `x · (2 − a·x)` | `~2⁶⁰` | ❌ `> 2⁵³` | ✅ | **JS 必须用 BigInt** |
| `4 · k · (n − k)` | `2²⁰` | ✅ | ✅ | — |
| `layer × 2048`（计数器基址） | `2³²` | ✅ | ✅ | 超过则 payload > 256 GiB，应报错 |

### 14.2 内存

**禁止**构造完整的三维数组。1 GiB 输入 = 8192 层，若每体素一字节就是 8 GiB 常驻。

规范的常驻内存上界（按 Node 参考实现的实测口径）：

| 缓冲 | 大小 | 说明 |
| --- | --- | --- |
| 输入层读缓冲 | 128 KiB | 流式读入的一层原始字节 |
| `S` 层填充序比特数组 | **0** | **不需要独立缓冲**：`S` 的打包约定（C2 MSB-first、`s = i mod L`）与输入文件切片的打包约定完全相同，因此输入层字节**就是** `S` |
| `O` 层存储序比特数组 | 128 KiB | 跨层复用 |
| 秩压缩位图 `B` | 128 KiB | 跨层复用，仅末层实际使用 |
| 秩压缩前缀和 `W`（`w = 32`） | 128 KiB | 跨层复用，仅末层实际使用 |
| ChaCha20 输出缓冲 | 128 KiB | 每层一次瞬时分配（`cipher.update()` 返回新缓冲） |

**常驻合计 ≈ 512 KiB + 128 KiB 瞬时 = 640 KiB，与文件总大小无关。**

> `S` 那行为 0 不是一个省略，而是一条**必须核对的性质**：只有当 `m` 恒为 8 的倍数（本格式成立，因为层按整字节切分）且位序约定一致时，输入切片才能直接当作 `S` 使用。若将来支持非整字节长度的输入（例如比特级容器），这一行就不再是 0。

### 14.3 位操作陷阱

1. **MSB-first 打包**（C2）：`byte |= bit << (7 − j)`，不是 `<< j`。写反会让每字节内 8 比特倒序，而往返测试**仍然通过**（编解码同源），只有黄金向量对拍能抓到。
2. **JavaScript 的 `>>` 是有符号右移**：对 ≥ 2³¹ 的值必须用 `>>>`。本格式的 `i` 上界是 `2⁴¹`（256 GiB = 2³⁸ 字节 × 8 = 2⁴¹ 比特），远超 2³¹，因此 JS 里**必须用 BigInt 或拆成高低位**处理全局比特序号；层内序号 `s < 2²⁰`、`q`、`r` 用普通 `Number` 安全。
3. **负数取模**：`(r − b) % 2²⁰` 在 C/JS/Rust 里对负数返回负值或实现定义值。必须先加模再取模：`((r − b) % M + M) % M`。
4. **`popcount`**：JS 没有内建，需要查表或 SWAR；Rust 有 `count_ones()`；Go 有 `bits.OnesCount64()`。

### 14.4 规格歧义（历史上最容易各写各的地方）

| 歧义点 | 规范裁定 | 出处 |
| --- | --- | --- |
| 螺旋起点 | 每圈左下角 `(k, k)` | §5.2 |
| 逆时针的参照系 | 从 +Z 向 −Z 俯视，`x` 右 `y` 上 | C3 / §5.2 |
| 边遍历顺序 | 下 → 右 → 上 → 左 | §5.2 |
| `m = 2` 的退化 | 四段各 1 格，覆盖 2×2 实心块 | §5.6 |
| 光栅方向 | `y` 升序（底行优先） | C4 |
| 满层是否多出一个空层 | 否，`layerCount = ceil(...)` | §3 / 判据 5 E3 |
| 末层是否补满 | 否，秩压缩到 `ceil(m/8)` 字节 | §7 |
| 位序 | MSB-first | C2 |
| 头部整数字节序 | 小端 | C1 |

### 14.5 已知的设计权衡（非缺陷）

| 权衡 | 选择 | 代价 |
| --- | --- | --- |
| 秩压缩需要预扫几何 | 接受 | 无法按比特流式解码；解码侧每层多一次 O(m) 位图重建 |
| 仿射散射在本挡位无安全贡献 | 仍保留 | 多 192 KiB 常驻内存与每层 2048 段初始化；换来 §12.5 的升级路径与判据 2 的成立 |
| `origSize` 明文 | 接受 | 泄露精确文件大小 |
| 层大小固定 128 KiB | 接受 | 小文件（< 128 KiB）只有一个末层，几何散射的收益低于大文件 |

### 15.3 每组向量的覆盖点

| 向量 | 覆盖点 | 若实现有错会怎样 |
| --- | --- | --- |
| GV-1 | `layerCount = 0`、纯头部、tag 覆盖空 payload | 空文件常被特殊处理而写错 |

| GV-6 | 跨层进位：满层 + `m = 8` 末层，两层用不同 counter 基址 | 计数器基址未乘 2048、或末层长度算错 |

### 15.4 为什么黄金向量不可省

判据 5（往返）对**编解码同源出错**是完全假绿的。实测注入的两个缺陷证明了这一点：

| 注入缺陷 | 判据 5 往返 | 判据 10 快慢对拍 | 黄金向量 |
| --- | --- | --- | --- |
| D5：位序写成 LSB-first | ✅ 绿 | ✅ 绿（快慢路径都用同一套位序） | ❌ **红**（首个差异字节偏移 0） |
| D6：圈内边序写成 下→上→右→左 | ✅ 绿 | ❌ **红** | ❌ **红** |

D5 是最危险的一类：它在本实现内部完全自洽，任何单机测试都抓不到，只有在与另一语言的实现对拍时才会暴露 —— 而那时数据可能已经写出去了。

### 16.4 Hensel 轮数的穷举验证

判据 13 只抽样 5000 个 `a`。轮数下界与上界另做一次**穷举**（`node -e`，遍历 `[1, 2²⁰)` 内全部奇数）：

| 轮数 | 不足的 `a` 个数 | 占比 |
| --- | --- | --- |
| 4 轮 | **262,144** / 524,288 | **50.00%** |
| 5 轮 | **0** / 524,288 | 0% |

最小的三个「4 轮不够」的奇数 `a`：**3, 7, 11**（三者 4 轮都得到 `a·x mod 2²⁰ = 983041`）。

> 这条穷举直接推翻了规格初稿的写法。初稿在 §11.2 写「需 19 次」，与同句「每轮精度翻倍」自相矛盾；而在判据里写「4 轮必然不足」又是**掷硬币式断言** —— 恰好 50% 的 `a` 四轮就收敛，派生出的 `a = 846561` 正落在收敛的那一半里，于是判据 13 首次运行就假失败。修法是把断言钉在一个**固定见证** `a = 3` 上，而不是钉在派生结果上。

### 16.6 吞吐

两组口径，差异来自 JIT 预热，都必须标注：

**口径 A：CLI 独立进程**（`node src/cli.js …`，每次冷启动，含文件 I/O，输入为随机字节，各跑一次）

| 尺寸 | 编码 | 编码吞吐 | 解码 | 解码吞吐 |
| --- | --- | --- | --- | --- |
| 1 MiB | 55 ms | 18.2 MiB/s | 69 ms | 14.5 MiB/s |
| 16 MiB | 844 ms | 19.0 MiB/s | 1102 ms | 14.5 MiB/s |
| 64 MiB | 3485 ms | 18.4 MiB/s | 4438 ms | 14.4 MiB/s |

**口径 B：单进程内连续跑**（JIT 已热，每次取样前强制 `global.gc()` 两次，含文件 I/O）

| 尺寸 | 编码吞吐 | 解码吞吐 |
| --- | --- | --- |
| 16 MiB | 21.0 MiB/s | 19.7 MiB/s |
| 64 MiB | 18.8 MiB/s | 18.1 MiB/s |
| 256 MiB | 20.8 MiB/s | 19.0 MiB/s |

口径 A 的解码比口径 B 慢约 20–25%，归因于冷进程的 JIT 未热（口径 A 每个尺寸都是独立进程）。**引用吞吐数字时必须带口径**，否则两组数看起来互相矛盾。

解码含两遍输入读取（第一遍只算 HMAC，第二遍才解码，见 §10.1），因此解码慢于编码是设计使然，不是实现缺陷。

### 16.7 常驻内存

测量方式：`node --expose-gc`，每次取样前调用 `global.gc()` 两次，取 `process.memoryUsage().rss`。

| 输入尺寸 | 基线 RSS | 编码后 | 增量 | 解码后 | 增量 |
| --- | --- | --- | --- | --- | --- |
| 16 MiB | 39.6 MiB | 44.7 MiB | **+5.0 MiB** | 44.6 MiB | +5.0 MiB |
| 64 MiB | 44.7 MiB | 45.2 MiB | **+0.5 MiB** | 45.4 MiB | +0.7 MiB |
| 256 MiB | 45.4 MiB | 47.2 MiB | **+1.8 MiB** | 47.2 MiB | +1.8 MiB |

三个尺寸的流式往返 SHA-256 全部一致。

**结论**：RSS 增量在 0.5–5.0 MiB 之间波动，**与输入尺寸无关**（256 MiB 输入只增 1.8 MiB），证实 §14.2 的「常驻内存与文件总大小无关」。

> **必须区分两个数字**：§14.2 按缓冲逐项加总得到的是 **640 KiB**（我刻意分配的量），而实测 RSS 增量是 **0.5–5.0 MiB**。差值来自 V8 分配器开销、`Buffer.allocUnsafe` 的池化行为与 GC 粒度 —— RSS 不是「我的缓冲之和」的精确度量。两个数字都真，但口径不同，不能混用。
>
> 首次测量曾得到「编码 64 MiB 后 RSS 增 22.4 MiB」，那是**测量方法错误**：加了 `--expose-gc` 却没调用 `global.gc()`，量到的是未回收的瞬时垃圾（每层 `cipher.update()` 都新建一个 128 KiB 缓冲，512 层共 64 MiB 垃圾）。加了强制 GC 后增量降到 0.5 MiB。

### 16.8 体积核对

| 输入 | 容器 | 差值 |
| --- | --- | --- |

## 17. 版本演进与兼容性

### 17.1 v1 的冻结项

以下内容在 v1 内**禁止**变更，任何改动都必须升 `version`：

- 头部 128 字节布局与各字段偏移；
- `flags` 的位定义与规范 profile 值 `0x1C`；
- 螺旋的起点、方向、边序；
- 仿射与秩压缩的定义；
- ChaCha20 的参数绑定方式；
- HKDF 的 `info` 字符串字面值。

### 17.2 解码方的兼容策略

| 遇到 | 必须的行为 |
| --- | --- |
| `version > 1` | 报「版本过新」，**禁止**尝试解析 |
| `flags` 含未支持位 | 报「不支持的 profile」，**禁止**静默降级 |
| `dimX ≠ dimY ≠ 1024` | 报「不支持的几何」 |
| `reserved` 非零 | 报「头部损坏」 |
| 文件长度 ≠ `origSize + 128` | 报「截断或有多余数据」 |
| `payload_tag` 不匹配 | 报「容器损坏」，**禁止**输出任何数据 |

**总原则：解码方遇到任何不符合规范的情况都必须硬失败，禁止尽力而为的部分还原。** 部分还原会让用户以为拿到了完整数据。

### 17.3 未来挡位

| 版本 | 计划变更 | 兼容性 |
| --- | --- | --- |
| v2 | `flags` bit5 启用每层压缩 | v1 解码方因 bit5 非零而硬失败 ✓ |
| v3 | 口令包裹 DEK（§12.5） | v1 解码方因 `version` 非 1 而硬失败 ✓ |
